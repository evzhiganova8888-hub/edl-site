## 0. Контекст патча

Запуск YooKassa 19.05.2026 вскрыл критический gap: PDF, который отдавался
клиенту, был «черновиком с watermark» и нарушал обещание сайта
(«PDF 10–15 стр на email за 24 часа»). Refund-риск через гарантию 14 дней —
P0. Решение разбито на 2 итерации, чтобы не блокировать запуск платежей.

## §2.3 шаг 2 — Бизнес-чекап (обновлено)

### Было (v1.4)

> **Plus 14к**: то же + 15 страниц + 7 рекомендаций + **персональное
> 15-мин видео от Кати**, которое автоматически отправляется через
> 24ч после оплаты на email клиента

### Стало (v1.5 patch)

- **Доставка PDF — сразу после завершения Чекапа клиентом** (ответ на
  последний вопрос → 5 мин на генерацию → PDF в Telegram-чат бота).
  Email-доставка добавится в Итерации 3 (когда настроится yandex 360 SMTP).
- **Plus-видео бриф Кате — через 24 часа после `checkup_completed`,
  а не после `payment_succeeded`.** Это решает кейс «клиент оплатил,
  но не прошёл Чекап неделю» — раньше Катя получала бесполезный бриф
  через 24 ч без ответов клиента.
- **SLA Кати на запись видео:** ≤ 24–36 часов после получения брифа.
  Авто-эскалация Ивану/Данилу при просрочке 12+ часов (Итерация 2).

### PDF содержит (Итерация 1, rule-based)

1. **Cover** (1 стр) — компания, имя, дата, тариф. Tangerine `#FF6B1A` в одной точке.
2. **Executive Summary** (1 стр) — главная боль + диагноз + ключевая
   рекомендация (rule-based из узких мест клиента).
3. **Диагноз по 4 слоям** (2–3 стр) — «Что сильно / Где разрыв /
   Риск 90 дней» по слою.
4. **5 (Base) / 7 (Plus) рекомендаций** — карточки с обязательными
   полями: заголовок, слой, что делать, инструмент, ответственный, первый
   шаг, что закрывает. Инструмент = тот, что клиент сам назвал (если
   нашли в ответах) или категориальный. Роль = по размеру команды.
5. **3 сценария** (2 стр) — Sniper / Combo / Full Stack по приоритетным
   метрикам клиента (см. §3.6).
6. **НДС-флажок 2026** (1 стр) — rules-based по выручке.
7. **Что входит / чего нет** (Plus only, 0.5 стр) — disclaimer об
   отличии от Диагностики.
8. **Upsell — Диагностика** (1 стр) — bullet-сравнение Чекап vs
   Диагностика, CTA `/start diagnostic`.
9. **Приложение — ваши ответы целиком** — компактный дамп.

**Watermark «ЧЕРНОВИК» снят.** Footer: «v1 · подготовлено @edl_os_bot ·
review by Катерина».

### PDF содержит (Итерация 2, LLM)

Те же 9 секций, но diagnosis_text + recommendations + scenarios генерирует
LLM по JSON-schema. Rule-based слой остаётся как fallback.

## §3.6 — 21-й уточняющий вопрос (НОВОЕ)

После ответа на 20-й вопрос (методологически Founder OS = 20 слоёв)
бот спрашивает один уточняющий — **3 главные метрики бизнеса клиента
в порядке приоритета**.

Не нумеруется как «21/21» — это **финальный штрих** для персонализации
3 сценариев под клиентские метрики, а не под средние по отрасли.

**Текст промпта:**

> Спасибо за развёрнутые ответы. Один уточняющий момент перед
> формированием PDF.
>
> Назовите 3 метрики вашего бизнеса, по которым вы судите о его здоровье.
> В порядке приоритета.
>
> Например: выручка / CAC / retention / маржа / NPS / utilization / runway.
> Можно своими словами.
>
> Это даст собрать сценарии под ВАШИ цифры, а не под средние по отрасли.

**Валидация:**
- Минимум 2 метрики (1 → мягкий переспрос).
- Максимум 5 (>5 → «выберите топ-3»).
- Эвристический парсер: словарь известных метрик (выручка, маржа, EBITDA,
  CAC, LTV, retention, churn, NPS, runway, utilization…) + наличие
  числа/процента/валюты.
- Не-метрики на первом проходе → один retry с уточнением. На retry —
  принимаем как есть, используем категориальные сценарии. См.
  `src/core/priority_metrics.py`.

Хранится в `Application.payload["priority_metrics"]`.

## §8.6 — PDF-генерация (НОВОЕ)

### Архитектура

```
clientcheckup_completed (ответ на 20-й + priority_metrics)
   ↓
generate_checkup_pdf (Celery task)
   ↓
   ├── [Итерация 1] render_report_v2 (rule-based) — src/core/checkup_report_v2.py
   │   ├── detect_team_size  (роли подбираются по размеру)
   │   ├── detect_tools      (упомянутые клиентом инструменты по слоям)
   │   ├── select_recommendations(plan)  (5 или 7)
   │   ├── build_scenarios(priority_metrics, recommendations)
   │   ├── executive_summary (на основе bottleneck'ов из ответов)
   │   └── _vat_section_dict
   │
   ├── [Итерация 2] LLM (Haiku 4.5 через proxyapi.ru, temp=0.2,
   │   max_tokens=4000) → JSON-schema → подмена diagnosis/recommendations/
   │   scenarios. 3 ретрая. Fallback → Итерация 1.
   │
   ↓
Jinja2 (src/templates/checkup_report_v2.html)
   ↓
WeasyPrint → PDF (10–15 стр)
   ↓
storage: относительный путь checkup_<uuid>.pdf
   (storage_root = /var/data/checkups на Railway, /tmp/edl_checkups локально)
   ↓
Telegram send_document клиенту
```

### Storage

В `Application.checkup_pdf_url` хранится **относительный путь**
(`checkup_<uuid>.pdf`), не абсолютный. Миграция в Selectel Object Storage
(когда поток > 50 Чекапов/мес) меняет только функцию `_pdf_storage_root()`
в `src/tasks/generate_checkup_pdf.py`. БД не трогается.

Helper `resolve_pdf_path()` принимает и относительные, и легаси-абсолютные
значения — обратная совместимость для PDF, сгенерённых до 19.05.

### Quality control (Итерация 2)

- Первые 20 LLM-Чекапов через inline-кнопки Кати в `/admin`:
  «✅ Одобрить → отправить» / «✍️ Доработать» / «❌ Перегенерировать».
- Auto-flags: LLM упомянул инструмент, которого клиент не называл → flag;
  рекомендация не относится к слою → flag; длина <30 / >150 слов → flag.
- После 20 чистых Чекапов → quality-gate сам решает: чистый → авто-отправка;
  любой flag → к Кате. Random 10% — на Итерации 3.

### Cost guard (Итерация 2)

- Глобальный per-час LLM budget уже есть (`src/core/rate_limit.py`).
- Per-Чекап лимит: **2 LLM-запроса максимум** (генерация + 1 retry при
  schema-fail). Логирование в `events` с типом `checkup_llm_call`.

## Demo access (без изменений vs v1.4 §3.3)

`/grant_demo <telegram_id|@username> [base|plus]` — admin-команда.

**Новое в v1.5 patch:**
