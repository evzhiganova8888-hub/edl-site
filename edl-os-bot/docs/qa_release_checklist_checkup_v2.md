# QA Release Checklist · Чекап v2.0

> **Цель:** перед прод-релизом Чекапа пройти этот чеклист руками на @edl_os_bot.
> **Среда:** прод, тестовые юзеры через `/grant_demo <tg_id>`.
> **Когда:** перед каждым deploy с правками Чекапа.
> **Кто:** Катя/Иван + QA.
> **Время:** ~90 мин полный проход; smoke (см. `qa_smoke_checkup_v2.md`) — 10 мин.
>
> **Шкала:** ✅ ОК · ⚠️ работает с замечанием · ❌ блокер релиза.

## P0 — критичные блокеры (деньги, юридика, потеря данных)

### P0.1 · Оплата + активация Чекапа

- [ ] **P0.1.1** Юзер `/start` → меню → `/audit` → выбор Base → ввод ФИО/email/компания → оферта `[✅ Я принимаю]` → видит сообщение «ожидает активации».
- [ ] **P0.1.2** Иван: `/applications pending` показывает заявку с inv_id и суммой 9 000 ₽.
- [ ] **P0.1.3** Иван: `/mark_paid <uuid> 9000 test-ref` → юзер получает уведомление «Чекап активирован» + кнопку `/checkup`.
- [ ] **P0.1.4** Повторный `/mark_paid <тот же uuid>` — **idempotent**, второй чек не создаётся, юзер не получает дубль уведомления.
- [ ] **P0.1.5** Plus (14 000 ₽) — тот же flow, но юзер видит фразу «+ видео-разбор от Кати».
- [ ] **P0.1.6** `refund_eligible_until` в БД — **точно 14 дней** от `payment_succeeded_at`. Проверка SQL: `SELECT refund_eligible_until - payment_succeeded_at FROM applications WHERE id = '<uuid>';` → `14 days`.

> ⚠️ **Известное расхождение с офертой:** оферта §6.4 говорит «14 дней с момента передачи Материалов» (PDF). Сейчас в коде — от `payment_succeeded_at`. Если юзер проходит Чекап >14 дней (пауза/работа), окно возврата истечёт раньше передачи PDF — нарушение оферты. **Перед релизом**: либо привести код к оферте, либо обновить оферту на «с момента оплаты». См. `qa_threat_matrix_checkup_v2.md` §L1.

### P0.2 · Возврат /refund

- [ ] **P0.2.1** Юзер сразу после `/mark_paid`: `/refund` → видит кнопку `[↩️ Получить возврат]` без подтверждения причины.
- [ ] **P0.2.2** Клик `[↩️ Получить возврат]` → создаётся `Refund(status='requested')`, юзер видит подтверждение, Иван получает алерт в `ADMIN_CHAT_ID`.
- [ ] **P0.2.3** **Безусловность:** юзер запрашивает возврат БЕЗ объяснения причины и БЕЗ упоминания «не смог внедрить» → принимается. (Оферта §6.1: «Причину указывать не нужно».)
- [ ] **P0.2.4** Через 14 дней `refund_eligible_until` истёк → `/refund` показывает «окно возврата закрыто» + контакт Ивана.
- [ ] **P0.2.5** Двойной запрос возврата (`/refund` 2 раза подряд) — второй раз говорит «заявка уже создана», не плодит дублей в БД.
- [ ] **P0.2.6** Текст в боте про возврат **совпадает с офертой** §6: «безусловный 14 дней», «причину не нужно». Если в боте сказано иначе — патчим `texts.py`.

### P0.3 · Данные не теряются и не утекают

- [ ] **P0.3.1** Юзер прошёл 15/20 → закрыл Telegram → через час `/checkup` → видит «Продолжить с вопроса 16/20» с правильным номером.
- [ ] **P0.3.2** `/reset` посреди Чекапа → context.user_data чист, НО `SELECT * FROM checkup_answers WHERE application_id = ...` — ответы на месте.
- [ ] **P0.3.3** Прохождение чекапа двумя устройствами (телефон + ноут одновременно) — последний ответ от любого устройства побеждает, нет race condition.
- [ ] **P0.3.4** `/delete_my_data` → User.email=NULL, User.first_name=NULL, pd_access_log пишет `action='delete'`. checkup_answers НЕ удаляются (нужны для агрегатной аналитики), но user_id обнуляется.
- [ ] **P0.3.5** PD-данные (email, телефон, INN, ФИО) **не попадают в логи Railway**. `httpx`/`httpcore` loggers на WARNING (не INFO).
- [ ] **P0.3.6** `BOT_TOKEN` не светится в логах Railway. Поиск `bot<token>` в логах за час → пусто.

### P0.4 · PDF доставка

- [ ] **P0.4.1** После Q20 → юзер видит «PDF готовлю, в течение 24 часов». PDF реально приходит в чат в течение **5 минут**.
- [ ] **P0.4.2** PDF содержит: имя клиента, дату, Score Чекапа, 4 слоя с цветами, **3 agent teaser-блока** (АНАЛИЗ/ПИСЬМО/МОНИТОР), CTA на Диагностику **45 000 ₽**, контакты, ссылку на оферту.
- [ ] **P0.4.3** PDF Plus содержит дополнительно: расширенные benchmarks, страницу «Спринт для вас», секцию «Видео-разбор от Кати» (placeholder до загрузки).
- [ ] **P0.4.4** Имя клиента в PDF — без экранирования HTML (если в company_name есть `<script>` или `&amp;`).
- [ ] **P0.4.5** Кириллица в PDF рендерится без квадратиков (Liberation/DejaVu шрифты в Dockerfile).
- [ ] **P0.4.6** PDF отправляется именно тому юзеру который покупал. Проверка: создать 2 paid Application'а у разных юзеров → PDF не путаются.
- [ ] **P0.4.7** Перегенерация PDF: `/regenerate_pdf <uuid>` создаёт новый PDF без дубля Application в БД.

## P2 — средний риск (полировка, мелкие баги)

### P2.1 · UX-полировка (паттерны TG для founders)

- [ ] **P2.1.1** **Прогресс-бар:** на каждом вопросе виден `📍 Вопрос 7/20 · ██████░░░░ 30%`. Соответствует реальному прогрессу.
- [ ] **P2.1.2** **Tone of voice:** на «вы», без панибратства, без аббревиатур (CAC/LTV/MRR) в Чекап-вопросах.
- [ ] **P2.1.3** **Авторитетные сигналы:** в intro упоминается «Бизнес-чекап EDL OS», «ИП Жиганова», ссылка на оферту.
- [ ] **P2.1.4** **Escape hatch на каждом экране:** есть `[💬 Написать Ивану]` или `[← В меню]`. Юзер никогда не «застревает».
- [ ] **P2.1.5** **Мобильный first:** длина сообщений до 4096 символов, кнопки full-width.
- [ ] **P2.1.6** **Эмодзи использованы как маркеры**, не как декорация: 📍📈⚙️💰 для слоёв, ✅❌ для статусов.
- [ ] **P2.1.7** **Скепсис к AI:** ни одно user-facing сообщение в Чекапе не содержит «AI рекомендует», «нейросеть посчитала». Всё подаётся как «Чекап», «методология», «Катя».
- [ ] **P2.1.8** **Гарантия возврата:** упомянута явно в intro («возврат 14 дней») и доступна через `/refund`.
- [ ] **P2.1.9** **Социальное доказательство:** `audit_sample.html` (пример отчёта) доступен через `/audit_sample` — снимает скепсис «купи кота в мешке».

### P2.2 · Edge cases input

- [ ] **P2.2.1** Длинный ответ (>4000 символов) — отклоняется с «слишком длинно».
- [ ] **P2.2.2** Спецсимволы NUL, control chars (`\x00`–`\x1F`) фильтруются `validate_user_text`.
- [ ] **P2.2.3** Markdown в ответе (`**жирный**`, `[link](url)`) — не интерпретируется как формат при отображении (хранится как text).
- [ ] **P2.2.4** Markdown injection в company_name типа `*Click here* <script>` — не ломает PDF.
- [ ] **P2.2.5** Юзер пишет ответ-картинку (sticker, photo) → бот отвечает «жду текст».

### P2.3 · Скрипты и сценарии видео

- [ ] **P2.3.1** Все 24 (+other = 28) сценария видео валидны: intro + focus + 4 layers + next_step.
- [ ] **P2.3.2** Никакой сценарий не содержит старой цены Диагностики (25 000).
- [ ] **P2.3.3** Сценарии адекватны сегменту/стадии — fact-check на 2–3 случайных.

### P2.4 · Аналитика и события

- [ ] **P2.4.1** События `checkup_started / question_answered / completed / paused / pdf_sent` пишутся в `events` table.
- [ ] **P2.4.2** `checkup_completion_rate` (completed / started за 7d) считается без ошибок.
- [ ] **P2.4.3** `mini_to_checkup_conversion` (paid checkups от Mini за 30d / Mini submissions за 30d) ≥ 5%.

### P2.5 · Admin-команды

- [ ] **P2.5.1** `/admin` — показывает 30-day метрики, ничего не падает.
- [ ] **P2.5.2** `/applications pending` — список с inv_id, email, плана.
- [ ] **P2.5.3** `/applications paid 5` — 5 последних paid.
- [ ] **P2.5.4** `/emails_dump` — CSV всех email (paid) скачивается без ошибок.
- [ ] **P2.5.5** Без `/admin_login` юзер не-в-ADMIN_USER_IDS получает «доступ запрещён».

### P2.6 · Конверсия и виральность

- [ ] **P2.6.1** CTA «Диагностика 45 000» в финале — текст ясный, не давит, понятна выгода.
- [ ] **P2.6.2** CTA Plus upsell — текст подчёркивает уникальность видео для именно его сегмента×стадии.
- [ ] **P2.6.3** PDF имеет share-friendly элементы: красивая обложка, имя компании на обложке, явно «Бизнес-чекап EDL OS» в шапке (для скриншотов в чатах).
- [ ] **P2.6.4** В PDF нет PD клиента (email, телефон, ИНН), которые он бы НЕ хотел шарить в публичной выписке.
